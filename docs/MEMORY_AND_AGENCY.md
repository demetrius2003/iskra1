# Долговременная память и agency (целевая линия развития)

**Версия документа:** 1.2  
**Дата:** 25 апреля 2026  
**Статус:** норматив для планирования; реализация по [TODO_MEMORY_AGENCY.md](TODO_MEMORY_AGENCY.md)  
**Комплект документации:** см. [VERSION](../VERSION)

**Бренд продукта** остаётся **Iskra-1** (пакет `iskra`). Нумерация релизов продолжается в SemVer (**0.4.0**, **0.5.0**, …). Ниже — целевые возможности, ранее обозначавшиеся в research как «Iskra-2»; в документации репозитория используем формулировку **«память + agency»** или **«расширенный режим памяти»**, без отдельного торгового имени продукта.

---

## 1. Видение («выход из коробки»)

Современные LLM между запросами **не существуют**: нет непрерывного внутреннего процесса, нет устойчивого опыта, который модель сама накапливает и пересматривает.

**Цель этой линии развития** — дать системе на базе Iskra-1:

1. **Persistent long-term memory** — сохраняемое между перезапусками и сессиями хранилище опыта: чтение, обновление, забывание, новые ассоциации между записями.  
2. **Manipulable self-modification (в пределах политики)** — влияние на **содержимое и использование** долговременной памяти и правил её обработки, **без** дообучения весов модели.

В результате система **существует между сообщениями пользователя**, порождает спонтанные мысли (как сейчас), опирается на прошлый опыт и может **менять поведение** на основе накопленного архива (в рамках конфигурации и уровней прав).

---

## 2. Отличия от текущего MVP (SQLite, «улитка»)

| Аспект | Сейчас (базовый режим) | Цель (эта линия) |
|--------|-------------------------|------------------|
| Память | SQLite, decay, стохастический recall | Постоянное хранилище, семантический поиск, граф связей, манипуляции по политике |
| Agency | Спонтанные мысли по таймеру | + активные запросы/предложения изменений памяти (теги протокола) |
| Права модели | По сути чтение + косвенное влияние через ответ | Уровни **L0–L3** (read-only → suggest → co-manage → full control по конфигу) |
| Состояние | Три переменные OU | + **emotional_valence**, **arousal**; **self-reflection** (по этапам) |
| Режим работы | Только тик цикла | Тик + обработка структурированных сигналов в ответе модели |

## 3. Модель записи памяти (целевая структура)

Логическая запись (**Memory Item**), для согласования реализации и CONFIG_SCHEMA:

| Поле | Смысл |
|------|--------|
| `id` | UUID |
| `timestamp` | Время создания/обновления |
| `content` | Текст воспоминания |
| `embedding` | Вектор (хранится в векторном слое) |
| `importance` | 0…1 |
| `emotional_valence` | −1…1 (опционально на ранних этапах) |
| `tags` | Метки для фильтрации |
| `links` | Идентификаторы связанных записей (граф) |
| `decay_rate` | Скорость забывания |
| `last_recall`, `recall_count` | Как в текущей модели |

**Бэкенды (ориентир):** векторный слой (например LanceDB / Chroma / Qdrant) + граф связей (на MVP — **NetworkX** в процессе; позже — Neo4j / ArangoDB при необходимости). Точный выбор — в задачах реализации и `pyproject` optional-dependencies.

---

## 4. Режимы доступа к памяти

**A. Пассивный (фоновый):** по триггеру цикла подмешиваются 1–3 записи (случайные или релевантные по смыслу), попадают в промпт / внутренний контекст.

**B. Активный (по инициативе модели):** в тексте ответа используются согласованные маркеры (см. §5). Парсер ядра извлекает намерение и выполняет его **в пределах `agency.level`**.

---

## 5. Уровни прав (**agency**)

| Уровень | Смысл |
|---------|--------|
| **L0** | Только чтение памяти |
| **L1 (Suggest)** | Модель **предлагает** сохранение/изменение; исполнитель ядра принимает решение (рекомендуемый старт) |
| **L2 (Co-manage)** | Как L1 для SAVE/UPDATE/links; **`importance`** в `[MEMORY_UPDATE]` не опускается ниже `agency.l2_importance_floor`; **`[MEMORY_DELETE]` запрещён**. |
| **L3 (Full control)** | Как L1/L2 по обновлениям (пол **не** применяется к `importance`); разрешён **`[MEMORY_DELETE]`**. |

Политика безопасности и аудит — по мере развития (см. CONFIG_SCHEMA). Периодическая **консолидация** Lance-памяти: `general.consolidation_every_n_ticks`. **Плановая саморефлексия:** `general.self_reflection_every_n_ticks` — после каждых N успешных тиков следующий тик выполняется как `trigger_type: self_reflection` (ядро подмешивает до `self_reflection_recall_n` воспоминаний в промпт; нужен `intent.user_prompts.self_reflection`).

**Граф ассоциаций:** рёбра имеют **вес** (в JSON — третий элемент `[u, v, w]` или пара `[u, v]` как вес 1). Повторный `link` / тег `links` **усиливает** связь (`memory.v2.graph_link_increment`, потолок `graph_max_edge_weight`). При `recall_graph_extra` соседи перебираются в порядке **убывания веса**; при консолидации дублей веса рёбер **складываются** (до потолка).

## 6. Теги протокола в тексте (утверждено)

Канонический синтаксис, правила кавычек и примеры — в [CONFIG_SCHEMA.md](CONFIG_SCHEMA.md), подраздел **«Протокол тегов в тексте ответа модели»**.

Кратко:

| Тег | Назначение |
|-----|------------|
| `[MEMORY_REQUEST]` | Запрос выборки/семантического поиска (`query: "…"`). |
| `[MEMORY_UPDATE]` | Изменение записи (минимум `id:` UUID; опционально `importance` и/или `links:` список UUID через запятую для рёбер графа). |
| `[MEMORY_SAVE]` | Новая запись (`content:` обязательно; опционально `importance` и др.). |
| `[MEMORY_DELETE]` | Удаление записи по `id:` — **только при L3**. |

Спонтанная мысль без тегов — как в текущем Iskra-1. При необходимости интеграций с внешним чатом позже можно ввести маркер вроде `[INTERNAL_THOUGHT]`.

## 7. Архитектурные точки изменения (один репозиторий `iskra`)

- **Memory Store** — новая реализация протокола (или расширенный контракт) + фабрика по `config`. Базовый SQLite остаётся для режима «как сейчас».  
- **Intent Generator** — переменные/шаблоны под семантический контекст и теги.  
- **State Engine** — новые переменные и правила feedback (по этапам).  
- **Trigger Engine** — триггеры, завязанные на память / консолидацию.  
- **MainLoop** — разбор ответа LLM на предмет тегов памяти; вызов политики agency.  
- **Config** — `memory.backend`, `memory.v2`, `agency.level`; см. [CONFIG_SCHEMA.md](CONFIG_SCHEMA.md) § «Расширенная память и agency». При несовместимости — поднять `CONFIG_SCHEMA_VERSION`.

**Обратная совместимость:** при текущем `schema_version` и отключённом расширенном режиме поведение **как у релиза 0.3.x** (без обязательных новых полей).
