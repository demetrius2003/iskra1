# Архитектура Iskra-1

> *«У улитки 10 000 нейронов. Но у неё уже есть интенция.»*
>
> Формальные контракты, типы данных и алгоритмы: [FORMAL_SPECIFICATION.md](FORMAL_SPECIFICATION.md)

## Философия проекта

Iskra-1 — это **фреймворк для выращивания искусственной интенции**. Не готовый продукт, а конструктор, в котором минимальное жизнеспособное ядро может расти годами, наращивая сложность — как живой организм.

Мы НЕ пытаемся построить человеческий мозг. Мы строим **улитку**: минимальную систему, которая уже демонстрирует спонтанное поведение и может масштабироваться горизонтально (новые модули) и вертикально (глубина каждого модуля) до произвольной сложности.

## Принцип минимальной интенции

Улитка (10 000 нейронов) обладает интенцией благодаря четырём вещам:

1. **Внутреннее состояние** — набор числовых переменных, описывающих «самочувствие» системы (аналог: голод, скука, тревога у улитки).
2. **Среда** — входящие сигналы извне (аналог: свет, влажность, запах пищи).
3. **Память** — записи прошлого опыта, влияющие на выбор действия (аналог: «тут была еда → ползу сюда»).
4. **Действие** — результат, порождаемый сочетанием состояния + среды + памяти (аналог: «поползла влево»).

Iskra-1 копирует именно эту минимальную схему, подставляя на место биологических компонентов программные абстракции.

## Компоненты ядра

### 1. State Engine (Двигатель состояния)

Набор числовых переменных, который **непрерывно эволюционирует во времени** по модели Орнштейна–Уленбека (случайное блуждание с возвратом к среднему). На старте (v0.01, «улитка») — 3 переменные:

| Переменная     | Диапазон  | Смысл                                           |
|----------------|-----------|--------------------------------------------------|
| `curiosity`    | [0.0, 1.0]| Склонность к новым темам → влияет на `new_topic` |
| `restlessness` | [0.0, 1.0]| Частота мыслей → модулирует интервал между тиками|
| `nostalgia`    | [0.0, 1.0]| Тяга к прошлому → влияет на `recall_memory`      |

Состояние меняется под действием трёх сил:
- **Время** — OU-дрейф: `dx = theta * (mu - x) * dt + sigma * sqrt(dt) * N(0,1)`
- **Внешние события** — мгновенные импульсы (пользователь написал → curiosity +0.15)
- **Обратная связь от LLM** — после recall_memory nostalgia снижается, после new_topic curiosity снижается (отрицательная обратная связь, предотвращающая зацикливание)

Масштабирование: новые переменные добавляются только через конфигурацию — ядро не меняется. Подробно: [STATE_ENGINE.md](STATE_ENGINE.md).

### 2. Trigger Engine (Генератор событий)

Работает непрерывно (демон). На каждом «тике» (переменный интервал 3–15 мин) смотрит на текущее состояние и решает: **породить мысль или промолчать**.

Минимальная логика (v0.01):
- Интервал: `base = max - (max - min) * restlessness`, с jitter ±10%.
- Тип мысли выбирается стохастически: `w_i = base_weight * (1 + strength * state[var])`, нормализуется в вероятности.
- 4 встроенных типа: `new_topic`, `recall_memory`, `continue_context`, `meta_reflection`.

Масштабирование: новые типы триггеров = новый файл + запись в конфиг. Подробно: [TRIGGER_ENGINE.md](TRIGGER_ENGINE.md).

### 3. Memory Store (Хранилище памяти)

Минимальная реализация (v0.01): **SQLite** с записями `{id, timestamp, category, content, importance, last_recall, recall_count, decay_rate}`.

Ключевые механизмы:
- **Recall** — стохастический выбор записей (score = importance * 0.7 + recency * 0.3).
- **Decay** — забывание: `importance *= (1 - rate * hours / 24)`. Часто вспоминаемые записи забываются медленнее.
- **Seed memories** — начальные воспоминания из YAML-файла, формирующие «личность».

Масштабирование: векторная база (Chroma/FAISS/LanceDB), граф связей (ArangoDB). Подробно: [MEMORY_SYSTEM.md](MEMORY_SYSTEM.md).

### 4. Intent Generator (Генератор намерений)

Получает `SparkEvent` от Trigger Engine и формирует `IntentPayload` — пару Jinja2-промптов (system + user), которые заставляют LLM воспринимать мысль как собственную. Подробно: [INTENT_GENERATOR.md](INTENT_GENERATOR.md).

### 5. LLM Adapter (Адаптер к модели)

**Async-интерфейс** для взаимодействия с любой LLM. Возвращает `LLMResponse` (текст + метрики). MVP: MockAdapter (без API) и OllamaAdapter (локальная модель). Retry и cooldown реализованы в MainLoop. Подробно: [GROK_INTEGRATION.md](GROK_INTEGRATION.md).

### 6. Output Channel (Канал вывода)

Куда уходит «мысль» после генерации. MVP: ConsoleOutput (rich/plain) и FileOutput (text/json). Потом — Telegram-бот, веб-интерфейс, голосовой синтез.

### 7. EventLog (Журнал событий)

Каждый полный цикл записывается в `events.jsonl` (JSON Lines). Содержит всё: state_before/after, промпты, ответ LLM, токены, latency, ошибки. Подробно: [EVENT_LIFECYCLE.md](EVENT_LIFECYCLE.md).

### 8. Внешний текст (опционально, `general.external_input_file`)

Путь в конфиге к **UTF-8** файлу: если в момент тика (при доступной LLM) в файле непустой текст, он попадает в `SparkEvent.metadata` и в промпты как **`external_input`** (Jinja2), плюс импульс `user_message` к состоянию. Источник — любой: Telegram, скрипт, ручное редактирование. Схема полей: [CONFIG_SCHEMA.md](CONFIG_SCHEMA.md) § `general`; жизненный цикл: [EVENT_LIFECYCLE.md](EVENT_LIFECYCLE.md).

## Принцип расширяемости

Каждый компонент — это **Python Protocol** (структурный интерфейс). Реализации подключаются через фабрики и конфигурацию. Пользователь фреймворка может:

- Добавить новую переменную состояния → только `config.yaml`.
- Написать свой тип триггера → новый файл + запись в конфиг.
- Подключить другой бэкенд памяти → реализовать `MemoryStore` Protocol.
- Подключить другую LLM → реализовать `LLMAdapter` Protocol.
- Подключить другой канал вывода → реализовать `OutputChannel` Protocol.
- Подмешать **внешний сигнал в цикл** → задать `general.external_input_file` (см. §8 выше и [CONFIG_SCHEMA.md](CONFIG_SCHEMA.md)); без отдельного канала ввода, только файловая очередь.

Ядро (`MainLoop`, `StateEngine`) **не меняется** при расширении. Конфигурация: [CONFIG_SCHEMA.md](CONFIG_SCHEMA.md).

## Чем это НЕ является

- Это НЕ chatbot.
- Это НЕ agent framework (LangChain, CrewAI и т.д.) — у них нет спонтанности.
- Это НЕ RAG-пайплайн — у RAG нет внутреннего состояния.
- Это НЕ cron job с промптами — у cron нет состояния и памяти, влияющих на решения.

Iskra-1 — это **первый шаг к тому, чтобы у LLM появилось "хочу", а не только "отвечаю"**.
