1. ЦЕЛЬ ПРОЕКТА

Создать фреймворк для выращивания искусственной интенции —
внешний программный модуль, который даёт любой LLM способность
к спонтанному порождению мыслей между пользовательскими запросами.

Фреймворк начинается с минимального жизнеспособного ядра
(уровень «улитка» — 3 переменных состояния, простая память,
стохастический триггер) и может масштабироваться до произвольной
сложности без переписывания основы.

═══════════════════════════════════════════════════════════════

2. КЛЮЧЕВАЯ ПРОБЛЕМА

Все существующие LLM (на апрель 2026) существуют только во время
forward-pass. Между запросами — полное отсутствие активности.
Человек (и даже улитка с 10 000 нейронов) обладает непрерывной
внутренней активностью и спонтанной интенцией.

Iskra-1 закрывает эту разницу ИЗВНЕ, не требуя модификации
самой языковой модели.

3. ТРЕБОВАНИЯ К MVP

3.1. Функциональные:
  - Автономный Python-демон, работающий в фоне.
  - State Engine: минимум 3 переменных внутреннего состояния
    (curiosity, restlessness, nostalgia), дрейфующих во времени.
  - Trigger Engine: случайный интервал (3–15 мин, модулируемый
    состоянием), стохастический выбор типа события.
  - Memory Store: хранение и извлечение воспоминаний с забыванием.
    Начальная реализация — SQLite.
  - Intent Generator: формирование промпта из события + состояния
    + памяти.
  - LLM Adapter: абстрактный интерфейс. На старте — MockAdapter
    (без API) и OllamaAdapter (локальная модель).
  - Output Channel: вывод «мыслей» в консоль (на старте).

3.2. Нефункциональные:
  - Каждый компонент — плагин за интерфейсом (Protocol).
  - Конфигурация через YAML-файл.
  - Логирование всех событий (для метрик).
  - Код на Python 3.12+, типизация, минимум зависимостей.

4. СЦЕНАРИИ ИСПОЛЬЗОВАНИЯ (USE CASES)

Пометки в критериях приёмки (ниже и в разделе 7):
  [ОБЯЗАТЕЛЬНО] — требование к первому исполняемому MVP.
  [ИССЛЕДОВАНИЕ] — целевая метрика для длительных прогонов и настройки;
    допускается отложить после появления стабильного демона.

UC-1. Первый запуск (Cold Start)
  Актор: Пользователь
  Предусловие: Python 3.12+ установлен, config.yaml подготовлен.
  Сценарий:
    1. Пользователь выполняет: python -m iskra
    2. Система валидирует config.yaml (Pydantic).
    3. Система инициализирует State Engine с начальными значениями.
    4. Система создаёт файл БД памяти (если не существует).
    5. Система загружает seed_memories (если указаны).
    6. Система применяет импульс "system_startup".
    7. Система выводит в консоль: "Iskra-1 запущена. Первый тик
       через N секунд."
    8. Через N секунд — первая мысль.
  Критерий приёмки:
    ✓ От команды до первой мысли — не более max_interval + 30 сек.
    ✓ Мысль содержит текст (не пустая строка).
    ✓ В консоли видны: timestamp, тип триггера, состояние.

UC-2. Непрерывная автономная работа (Steady State)
  Актор: Система (без участия пользователя)
  Предусловие: Система запущена и работает > 1 часа.
  Сценарий:
    1. Каждые min_interval..max_interval секунд система
       порождает мысль.
    2. Переменные состояния дрейфуют по OU-модели.
    3. Типы триггеров варьируются (не один и тот же тип подряд
       10 раз — это статистически маловероятно).
    4. Мысли записываются в Memory Store.
    5. Старые воспоминания теряют importance (decay).
    6. Иногда система «вспоминает» прошлую мысль (recall_memory).
    7. Все события записываются в events.jsonl.
  Критерий приёмки:
    ✓ [ОБЯЗАТЕЛЬНО] За 24 часа — 0 необработанных исключений (graceful errors OK).
    ✓ [ИССЛЕДОВАНИЕ] Энтропия Шеннона по trigger_type за сутки > 1.0 бит
      (т.е. не застревает на одном типе).
    ✓ [ИССЛЕДОВАНИЕ] Хотя бы 10% событий содержат memory_context != []
      (система использует память).
    ✓ [ИССЛЕДОВАНИЕ] Средний дрейф state_variables: variance > 0.001
      (переменные реально меняются).

UC-3. Настройка через конфигурацию (Config Tuning)
  Актор: Пользователь
  Предусловие: Система работала с конфигом A.
  Сценарий:
    1. Пользователь останавливает демон (Ctrl+C).
    2. Редактирует config.yaml: увеличивает curiosity.sigma
       с 0.08 до 0.20, уменьшает min_interval до 60.
    3. Перезапускает: python -m iskra
    4. Наблюдает: мысли приходят чаще, curiosity колеблется
       сильнее, больше new_topic.
  Критерий приёмки:
    ✓ Изменение конфига НЕ требует правки кода.
    ✓ Невалидный конфиг → понятное сообщение об ошибке + exit(1).
    ✓ Поведение системы наблюдаемо отличается при разных конфигах.

UC-4. Подключение Ollama (Real LLM)
  Актор: Пользователь
  Предусловие: Ollama запущен локально с моделью llama3:8b.
  Сценарий:
    1. В config.yaml: llm.adapter = "ollama".
    2. Запуск: python -m iskra
    3. Система проверяет доступность Ollama (is_available).
    4. При каждом тике — реальный запрос к LLM.
    5. Ответ LLM выводится как «мысль».
    6. Ответ анализируется (feedback) и влияет на состояние.
    7. Ответ сохраняется в Memory Store.
  Критерий приёмки:
    ✓ Мысли — связный текст на естественном языке.
    ✓ При недоступности Ollama — система НЕ падает,
      пишет warning в лог и ждёт следующего тика.
    ✓ Обратная связь работает: после recall_memory
      значение nostalgia снижается.

UC-5. Работа без LLM (Mock Mode)
  Актор: Разработчик
  Предусловие: llm.adapter = "mock" в конфиге.
  Сценарий:
    1. Запуск: python -m iskra
    2. Система работает в полном объёме: State Engine дрейфует,
       Trigger Engine срабатывает, Memory Store работает.
    3. Вместо LLM — шаблонный ответ (template из конфига).
    4. Все метрики и логи работают как обычно.
  Критерий приёмки:
    ✓ Нулевые внешние зависимости (нет сетевых запросов).
    ✓ Полезен для отладки State Engine и Trigger Engine.
    ✓ events.jsonl содержит корректные записи.

UC-6. Добавление нового типа триггера (Plugin)
  Актор: Разработчик-контрибьютор
  Предусловие: Хочет добавить триггер "time_aware" (утром
    бодрее, ночью задумчивее).
  Сценарий:
    1. Создаёт файл iskra/triggers/time_aware.py с классом,
       реализующим TriggerType Protocol.
    2. Добавляет в config.yaml:
       trigger.types.time_aware:
         base_weight: 0.10
         modulated_by: null
         context_source: "system_clock"
    3. Перезапускает систему.
    4. Новый тип триггера используется наравне с остальными.
  Критерий приёмки:
    ✓ Ядро системы (main_loop, state_engine) НЕ изменено.
    ✓ Новый триггер появляется в events.jsonl.
    ✓ Удаление триггера из конфига → система работает без него.

UC-7. Анализ метрик (Post-hoc) [ИССЛЕДОВАНИЕ — весь сценарий]
  Актор: Исследователь
  Предусловие: Система проработала 48 часов,
    events.jsonl содержит ~200 событий.
  Сценарий:
    1. Исследователь открывает events.jsonl.
    2. Строит график state_before.curiosity во времени.
    3. Считает распределение trigger_type.
    4. Считает среднюю длину ответа LLM.
    5. Проверяет: коррелирует ли curiosity с частотой new_topic?
  Критерий приёмки:
    ✓ [ИССЛЕДОВАНИЕ] Данных достаточно для построения графиков.
    ✓ [ИССЛЕДОВАНИЕ] Формат JSONL парсится стандартным json.loads().
    ✓ [ИССЛЕДОВАНИЕ] Корреляция curiosity ↔ p(new_topic) > 0.3.

6. ТЕХНОЛОГИЧЕСКИЙ СТЕК (MVP)

  - Python 3.12+
  - asyncio (встроен — основной цикл)
  - SQLite (встроен — нулевые зависимости для памяти)
  - PyYAML (конфигурация)
  - Pydantic (валидация конфигурации)
  - Jinja2 (шаблоны промптов)
  - Опционально: httpx (для API-адаптеров)
  - Опционально: rich (красивый вывод в консоль)

Никаких тяжёлых зависимостей (Mem0, Chroma, LangChain и т.д.)
на этапе MVP. Добавляются позже как плагины.

Полный обзор технологического ландшафта — в TECHNOLOGIES.md (каталог docs/).

7. КРИТЕРИИ ПРИЁМКИ MVP (ACCEPTANCE CRITERIA)

Пометки [ОБЯЗАТЕЛЬНО] / [ИССЛЕДОВАНИЕ] — как в разделе 4.

AC-1. Запуск:
  ✓ [ОБЯЗАТЕЛЬНО] python -m iskra запускает демон с единственным аргументом
    --config (опционально).
  ✓ [ОБЯЗАТЕЛЬНО] Невалидный конфиг → понятная ошибка + exit(1).
  ✓ [ОБЯЗАТЕЛЬНО] Двойной запуск → "Already running" + exit(1) (pid-файл).

AC-2. Стабильность:
  ✓ [ОБЯЗАТЕЛЬНО] Работает минимум 24 часа без НЕОБРАБОТАННЫХ исключений.
  ✓ [ОБЯЗАТЕЛЬНО] Ошибки LLM/сети/памяти обрабатываются gracefully.
  ✓ [ОБЯЗАТЕЛЬНО] Ctrl+C → корректное завершение (graceful shutdown).

AC-3. Автономность:
  ✓ [ОБЯЗАТЕЛЬНО] Порождает мысли БЕЗ участия пользователя.
  ✓ [ОБЯЗАТЕЛЬНО] Мысли приходят с переменным интервалом (не фиксированным).
  ✓ [ИССЛЕДОВАНИЕ] Типы триггеров варьируются (энтропия Шеннона > 1.0 бит).

AC-4. Зависимость от состояния:
  ✓ [ИССЛЕДОВАНИЕ] При высокой curiosity — больше new_topic.
  ✓ [ИССЛЕДОВАНИЕ] При высокой nostalgia — больше recall_memory.
  ✓ [ИССЛЕДОВАНИЕ] Переменные состояния дрейфуют (variance > 0.001 за сутки).
  ✓ [ОБЯЗАТЕЛЬНО] Обратная связь от LLM изменяет состояние.

AC-5. Память:
  ✓ [ОБЯЗАТЕЛЬНО] Мысли сохраняются в Memory Store.
  ✓ [ОБЯЗАТЕЛЬНО] Система вспоминает прошлые мысли (recall_memory работает).
  ✓ [ОБЯЗАТЕЛЬНО] Старые записи теряют importance (decay работает).
  ✓ [ОБЯЗАТЕЛЬНО] Часто вспоминаемые записи забываются медленнее.

AC-6. Конфигурируемость:
  ✓ [ОБЯЗАТЕЛЬНО] Все параметры — в config.yaml, не в коде.
  ✓ [ОБЯЗАТЕЛЬНО] Добавление новой переменной состояния — только конфиг.
  ✓ [ОБЯЗАТЕЛЬНО] Переключение LLM-адаптера — только конфиг.
  ✓ [ОБЯЗАТЕЛЬНО] Шаблоны промптов — в конфиге.

AC-7. Расширяемость:
  ✓ [ОБЯЗАТЕЛЬНО] Новый тип триггера = новый файл + запись в конфиг.
  ✓ [ОБЯЗАТЕЛЬНО] Новый LLM-адаптер = новый файл + запись в конфиг.
  ✓ [ОБЯЗАТЕЛЬНО] Новый канал вывода = новый файл + запись в конфиг.
  ✓ [ОБЯЗАТЕЛЬНО] Ядро системы НЕ меняется при расширении.

AC-8. Наблюдаемость:
  ✓ [ОБЯЗАТЕЛЬНО] events.jsonl содержит полную историю событий.
  ✓ [ОБЯЗАТЕЛЬНО] Каждое событие: id, timestamp, trigger_type, state_before,
    state_after, prompt, response, tokens, latency, errors.
  ✓ [ИССЛЕДОВАНИЕ] Данных достаточно для построения графиков и метрик.

8. ПРИНЦИП МАСШТАБИРОВАНИЯ

Фреймворк растёт как живой организм:
  - Новые переменные состояния → расширяют пространство
    «настроений».
  - Новые типы триггеров → новые «органы чувств» (RSS, погода,
    Telegram, ...).
  - Новые бэкенды памяти → от SQLite до векторных баз и графов.
  - Новые LLM-адаптеры → от Mock до GPT-4 / Grok / Claude.
  - Новые каналы вывода → от консоли до голосового синтеза.

Каждое расширение — это добавление, а не замена.
Ядро остаётся стабильным.

10. ИСТОРИЧЕСКАЯ СПРАВКА

Проект родился из философской переписки с Grok о природе
вложенных реальностей и различиях между человеческим сознанием
и архитектурой LLM. Ключевое наблюдение: у человека есть
непрерывный внутренний поток мыслей (даже если 99% из них —
шлак), у LLM — только дискретные вспышки по запросу. Именно
эта разница породила идею «внешней искры».

Черновики и история переписки — в каталоге research/ (например research/iskra.txt).
